# Immutable CDN publication

Production runs `archives`, `prepare`, then `publish` via `cli.js`. No dependencies are required beyond Node, GNU tar, gzip and the AWS CLI already installed on the deploy runner. On macOS use `CDN_TAR=gtar` for archives.

- `archives` sorts tar entries, fixes mtime to Unix epoch and numeric owner/group to 0, normalizes file/directory modes to 0644/0755, and uses `gzip -n`. Existing archives and generated listing HTML are excluded, including on reruns. Nonproduction deployments retain their existing archive behavior.
- `prepare` assembles SDK v3, v1.1 and loader trees in `.cdn-publication/`. Component HTML uses sorted local manifest entries and SRI digests instead of S3 timestamps. URLs refer to the corresponding version. Each versioned tree contains `manifest.json`: `<sdk version>/manifest.json`, `<v1.1 version>/manifest.json` and `js-sdk-loader-scripts/<loader version>/manifest.json`. The manifest omits itself to avoid a circular digest; publication derives its digest from its local bytes and includes it in all checks. The deploy workflow does not modify GitHub releases; it preserves all three manifests in the `cdn-release-manifests` workflow artifact (under `sdk/`, `legacy/` and `loader/`). SDK runtime code does not consume these manifests yet.
- Completeness checks run before writing a release manifest and again when loading it for publication. Both variants require their production core bundle and every integration in the same catalog used for names/display names. Production browser targets publish external maps, so their maps are required too. The modern plugin tree must contain `rsa-plugins.js` (the federation remoteEntry), every exposed plugin bundle, and all relative JavaScript references in every plugin chunk, including static imports, dynamic imports and the federation module map. Missing files are reported together; deleting files and regenerating inventory cannot bypass the check.
- `publish` validates all local trees, then fully paginates and preflights **all** versioned prefixes with trailing slashes before the first production upload. Extra keys or changed bytes fail with instructions to release a new version. Identical existing objects are skipped; a partial identical tree can be completed. Each new object uses `put-object --if-none-match '*'`; concurrent collisions must have identical bytes, including loader files and the manifest. AWS errors propagate.
- The manifest is uploaded last within each prefix, only after all other objects pass S3 and CDN verification. After uploading the manifest, the prefix is invalidated again and the complete tree is verified, including the manifest. After each upload, CloudFront invalidation must finish. Verification requires exact S3 key-set equality and matching SHA-384 for every decoded CDN response body, including archives, maps, HTML and the manifest. It requires HTTP 200, uses at most eight requests concurrently, a 30-second timeout per request, and four attempts with 1/2/4-second backoff. All trees must pass before the workflow promotes any moving production path. Versioned v1.1 invalidation therefore runs only in production.
- The reusable workflow validates both moving destination inputs before building or uploading. Only `v3`, `v1.1`, their `staging/latest` and `dev/latest` paths, and `beta/PR-<number>/<hex SHA>/v3|v1.1` are allowed. Version-like segments and alternate spellings fail closed.
- Rollback asserts that its destinations are exactly `v3/`, `v1.1/` and `js-sdk-loader-scripts/latest/`. Moving environment, beta, Adobe and sanity prefixes remain writable.

Run tests with `npm run test:cdn-publish`; the unit-tests-and-lint workflow runs them beside the vendor hash utility tests. To prepare built production trees without AWS access, run `node scripts/cdn-publish/cli.js archives` then `BASE_CDN_URL=https://cdn.rudderlabs.com node scripts/cdn-publish/cli.js prepare`. Generation for an individual built tree is also available through `writeManifest(root, { sdk: { name, version } })` in `publication.js`.

The release manifest uses stable two-space JSON with a trailing newline, resources sorted by relative path and no timestamps:

- `schemaVersion`: `1`.
- `sdk`: package `name` and released `version` (v3, v1.1 or loader).
- `resources`: entries with `type`, `variant` (`modern`, `legacy` or `null`), `path` (exact served file relative to the versioned prefix), `integrity` (`sha384-<base64>`) and `size` (bytes).
- Types: `core`, `plugin`, `integration`, `loader`, `listing`, `archive`, `sourcemap`, `other`. Integration entries also have `name` (SDK filename-building name) and `displayName`, joined from `config_to_integration_names.js` and the generated integration `Destinations.ts` constants. Unknown integration JavaScript fails generation. Exposed plugin entries have `name` from Rollup's exposed-plugin map; shared chunks, the index module and federation entry points are `plugin` without an individual `name`. Maps use `sourcemap` even for integration/plugin code.

Readers ignore unknown fields. Additive changes keep `schemaVersion`; breaking changes bump it. The publisher validates known fields and file bytes while allowing additive metadata.

Infrastructure must enforce the same contract: deny `DeleteObject` and `DeleteObjectVersion` on versioned keys, require `If-None-Match` on versioned `PutObject`, and seal completed prefixes against additions. This workflow cannot prevent another principal from adding/deleting keys after verification. Older versions with different bytes must be released under a new version, including hotfixes; reruns never repair them by overwriting.
